# gpt-6-astra advisory: the small-turn prefill levers (2026-09-08)

Reviewer: gpt-6-astra via codex exec (read-only sandbox, xhigh), static review of BUILDLOG 2026-09-08 (k), the plan's phase 3 status, generate_prefill / prefill_chunk / the GDN and attention prefill kernels, the WY scan and the attention split launcher. Asked to rank levers A (mid-chunk snapshot), B (last token into the batched chunk), C (attention split on underfill), find cheaper levers, and say what to do first. Dispositions in BUILDLOG 2026-09-08 (l); the order is now the plan's phase 3 continuation.

## Report (reviewer's words)

**Rank A/B/C by value per risk and effort: C → B → A. Start tomorrow with a cheaper, bitwise candidate: capture DFlash2’s tapped last-token forward in a CUDA graph.** C reuses an existing mechanism with limited plumbing; B removes a weight stream but changes the prefill-to-decode contract; A offers the largest individual saving and has the most snapshot/cache complexity. Splitting A’s GDN scan can preserve that scan’s arithmetic, but it does **not** make the merged forward bitwise with today’s dispatch. The quoted savings are useful hypotheses, overlap, and need measurement after each change. This review was static; nothing was built, executed, or changed.

1. **[P1] Capture the tapped last-token forward first — approximately ½–1 session.**

   The ordinary `step_with` already replays `graph_exec`; DFlash2 instead calls `token_launches(d2_vtaps)` eagerly so the last prompt position reaches its ring. `token_launches` explicitly contains no synchronization or allocation and already supports capturing its five tap copies. Evidence: [engine.cuh:1551](/mnt/ai/projects/q27/src/engine.cuh:1551), [engine.cuh:5095](/mnt/ai/projects/q27/src/engine.cuh:5095), [engine.cuh:5248](/mnt/ai/projects/q27/src/engine.cuh:5248).

   Capture a separate graph after DFlash2 allocates `d2_vtaps`, before serving requests. Replay the **same greedy forward, head, argmax and advance**, then retain the existing one-row `ingest` outside the graph: ingestion has host position/coverage bookkeeping. Preserve the synchronous token upload and the previous-round fold-event dependency. Evidence: [engine.cuh:2849](/mnt/ai/projects/q27/src/engine.cuh:2849), [engine.cuh:4855](/mnt/ai/projects/q27/src/engine.cuh:4855), [dflash2.cu:611](/mnt/ai/projects/q27/src/dflash2.cu:611).

   This is a credible **bitwise** change. Budget roughly **3–5 ms**, conditional on measurement: the reported eager step contains approximately 5 ms of submission overhead, while its 8.3 ms GEMV weight traffic remains. It also helps `pf=1`, where A, B and C may have no useful batched work. Gate on identical final logits, normalized hidden state, recurrent state, live KV/tap rows, position counters and seeded warm-turn streams—not merely identical first argmax. The missing last-token ring row previously cost measurable acceptance, so retaining that row is load-bearing. Evidence: [BUILDLOG.md:15738](/mnt/ai/projects/q27/docs/BUILDLOG.md:15738), [BUILDLOG.md:16353](/mnt/ai/projects/q27/docs/BUILDLOG.md:16353).

2. **[P1] C ranks first: extend the existing attention split cautiously — approximately 1–2 sessions including focused gates.**

   Both MMA launcher branches choose the default split count from `(base_pos + t0 + SB)/4096`, clamped to eight. The mechanism, partial buffer and combine kernel already exist. Preserve `part != nullptr`, `t0 == 0`, explicit overrides and the current deep-context behavior when adding an underfill criterion. The `t0` restriction prevents a documented mismatch between absolute partial-write indices and relative combine indices. Evidence: [prefill.cu:2531](/mnt/ai/projects/q27/src/prefill.cu:2531), [prefill.cu:2582](/mnt/ai/projects/q27/src/prefill.cu:2582).

   One correction matters for sizing: the current unsplit grid is **`4 × ceil(T/16)`**, meaning 4/8/12/16 blocks through T=16/32/48/64. Eight splits therefore give only 32 blocks for a five-token tail. Use underfill to propose a split count, then constrain it by useful 32-position tiles and enough work to amortize combine. Do not interpret “blocks < SMs” as sufficient justification to split a nearly empty cold context. The estimated **up to 4.5 ms per affected chunk** remains plausible, not established. Evidence: [prefill.cu:2537](/mnt/ai/projects/q27/src/prefill.cu:2537), [prefill.cu:2067](/mnt/ai/projects/q27/src/prefill.cu:2067).

   **Numerics:** this is P4’s mechanism and tolerance-policy class, not bitwise. Furthermore, production’s `pv8` path casts softmax weights to e4m3; changing local maxima under splitting can change those rounded operands as well as the FP32 combine order. Do not borrow P4’s historical `1.9e-5` observation as a guaranteed bound. Evidence: [prefill.cu:2228](/mnt/ai/projects/q27/src/prefill.cu:2228), [prefill.cu:2257](/mnt/ai/projects/q27/src/prefill.cu:2257), [BUILDLOG.md:139](/mnt/ai/projects/q27/docs/BUILDLOG.md:139).

   C needs no new snapshot or token-position machinery, but changed attention outputs propagate into later KV rows, GDN state, DFlash2 taps and MTP warming. Gate the actual production `pv8` branch on shallow/deep contexts, ragged queries, empty splits, scattered KV pages and the eight-split scratch limit. The named current split test uses T=37, base=9000 and half KV; that alone does not cover this extension. Include turn replay, distribution quality and DFlash2 acceptance checks described below. Evidence: [test_kernels.cu:2209](/mnt/ai/projects/q27/src/test_kernels.cu:2209).

3. **[P1] B ranks second: merge the last token into an existing post-snapshot chunk — approximately 1–2 sessions for DFlash2, 2–3 for all modes.**

   Begin with the narrow case: an existing chunk **after** the snapshot has room for one more token. That merges chunk B and the eager step without implementing A. Keep the current path when only one token remains, the preceding chunk is full, or appending would cross the snapshot boundary. Creating a new one-token batched chunk would retain the weight stream and could be slower. The loops currently stop at `NP-1`; snapshots can also use the `NP-1` fallback when `stable_len <= base`, so blindly changing both loop limits is incorrect. Evidence: [engine.cuh:5040](/mnt/ai/projects/q27/src/engine.cuh:5040), [engine.cuh:5078](/mnt/ai/projects/q27/src/engine.cuh:5078).

   After forwarding through position `NP-1`, retain that row’s `output_norm(hT)` in engine-owned `x1`. Run the existing **`qx` plus `mm(output.weight)`** head GEMV, argmax and advance. Preserve `logits` for sampling, `h_next`, `d_P=P_out=NP-1`, and the advance result `d_pos=d_step=NP`, including the generated-token write. Using the verify fast head would add another numerical change. Evidence: [engine.cuh:1582](/mnt/ai/projects/q27/src/engine.cuh:1582), [blocks.cu:127](/mnt/ai/projects/q27/src/blocks.cu:127), [engine.cuh:5141](/mnt/ai/projects/q27/src/engine.cuh:5141).

   Two concrete traps require explicit handling. **MTP:** warm only rows with a known successor token; the final row cannot read `prompt[NP]`. Save its normalized hidden state before warming, because `mtp_warm_T` overwrites `x1T`. **DFlash2:** seed position `NP-1` through the batched taps exactly once, remove its separate ingestion, and leave `d2_prefill_done` seeing the new pending token with committed position `NP-1`. Evidence: [engine.cuh:3921](/mnt/ai/projects/q27/src/engine.cuh:3921), [engine.cuh:2956](/mnt/ai/projects/q27/src/engine.cuh:2956).

   **Numerics:** B is eligible for acceptance under the g64 policy, but that policy is not prior validation of B. The final token changes from g32/serial projections, `delta_step` and decode attention to g64 projections, WY and prefill attention. Keeping the head GEMV does not recover the old hidden state. There is no straightforward bitwise version of this proposed default path. The g64 precedent explicitly substitutes kernel tolerance, corpus quality and unchanged serial canonicals for serial/batched identity. Evidence: [engine.cuh:1465](/mnt/ai/projects/q27/src/engine.cuh:1465), [engine.cuh:3823](/mnt/ai/projects/q27/src/engine.cuh:3823), [BUILDLOG.md:349](/mnt/ai/projects/q27/docs/BUILDLOG.md:349).

   Gate first-token distributions specifically, plus subsequent continuations and restore behavior. Keep the sampled bootstrap at position **NP, draw kind 0**; prefill still prepares a greedy pending token that sampling replaces later. Also preserve the CLI threshold: the production server sets `pf_batch_min=2`, whereas the default five-token canonical stays serial at 32. Evidence: [engine.cuh:4563](/mnt/ai/projects/q27/src/engine.cuh:4563), [engine.cuh:2988](/mnt/ai/projects/q27/src/engine.cuh:2988), [server.cu:505](/mnt/ai/projects/q27/src/server.cu:505).

4. **[P2] A ranks third: valuable, but requires a boundary-state design — approximately 3–5 sessions.**

   The stable boundary is immediately before the trailing assistant opener; the thinking template is volatile. Split encoding preserves the shared token prefix across re-rendered turns. Moving the snapshot to the merged chunk’s end would defeat that purpose. Evidence: [api_common.h:679](/mnt/ai/projects/q27/src/api_common.h:679), [api_common.h:804](/mnt/ai/projects/q27/src/api_common.h:804), [server.cu:2748](/mnt/ai/projects/q27/src/server.cu:2748).

   Capture **both** `S[il]` and the three raw-QKV convolution-history rows at the boundary for every recurrent layer. The ring is not reconstructed from normalized `convT`; for cuts smaller than three tokens it also needs incoming history. A practical first design merges weight projections but retains two convolution/scan segments per GDN layer, copying their boundary state before the second segment advances it. Attention can causally consume a merged batch after writing its KV rows: each query must retain its own absolute causal limit. Evidence: [engine.cuh:4061](/mnt/ai/projects/q27/src/engine.cuh:4061), [prefill.cu:1242](/mnt/ai/projects/q27/src/prefill.cu:1242), [engine.cuh:3853](/mnt/ai/projects/q27/src/engine.cuh:3853).

   **The scan-only bitwise answer is yes, conditionally:** two calls on the original subranges preserve WY’s original 64-token grouping, given identical inputs and incoming state. They also preserve the chosen sequential implementation. An uninterrupted WY scan generally does not: its log-prefix calculation and state updates are grouped by local 64-token blocks. Calling `delta_scan_seq` instead is bitwise with serial `delta_step`, **not** with today’s default WY. Also, `Q27_DS_MODE=seq` alone still defaults to the reassociated column-split scan; the direct exact leg additionally requires `Q27_DS_SPLIT=1`. Evidence: [prefill.cu:2995](/mnt/ai/projects/q27/src/prefill.cu:2995), [prefill.cu:3201](/mnt/ai/projects/q27/src/prefill.cu:3201), [prefill.cu:3293](/mnt/ai/projects/q27/src/prefill.cu:3293).

   **The whole-forward bitwise answer is no for a naive merge.** GEMM token-tile width is bitwise invariant, but split-K selection is not. For example, a 5120-row projection on 170 SMs uses three splits at T=36 and four at T=5; merging to T=41 uses three for both portions. Attention merging can also change query-tile endpoints and hence position partitions. A genuinely bitwise variant must preserve those per-segment reductions and attention geometry, or restrict eligibility to proven-equivalent shapes. That is possible engineering, but it sacrifices some simplification and payoff. Evidence: [prefill.cu:735](/mnt/ai/projects/q27/src/prefill.cu:735), [prefill.cu:862](/mnt/ai/projects/q27/src/prefill.cu:862), [prefill.cu:2067](/mnt/ai/projects/q27/src/prefill.cu:2067).

   The largest correctness trap is persistence: `snap_save`, `ckpt_save` and `pfx_export` currently copy **live** recurrent state. After merging, live state is past the boundary. Publishing it with boundary token metadata would create an internally inconsistent cache. Export the captured boundary state explicitly; retain attention rows `[0,L)` and the existing MTP `[0,L+1)` contract. Publish only after all layers’ boundary state is complete. Review overlapping checkpoint validity when rewritten KV rows can acquire different numerics—the current retention argument assumes identical rewrites. Evidence: [engine.cuh:3976](/mnt/ai/projects/q27/src/engine.cuh:3976), [engine.cuh:4206](/mnt/ai/projects/q27/src/engine.cuh:4206), [engine.cuh:4104](/mnt/ai/projects/q27/src/engine.cuh:4104), [engine.cuh:4985](/mnt/ai/projects/q27/src/engine.cuh:4985).

   Gate boundary snapshots and restored continuations across cuts near 1/2/3, 16/32/64 and 1024 tokens, all prefix-hit tiers, branch divergence and repeated prompts. Preserve chronological DFlash2 ingestion, seed-window clipping and ring compaction; compare relevant ring rows by absolute position because merging changes ingestion batch boundaries. Keep each merged chunk within `PF_T`.

5. **[P2] Tiny verify-style prefill is worth a later experiment; it is not a drop-in shortcut.**

   The verify forward already amortizes weights across known token lanes and writes causally addressed KV. That makes a dedicated tiny-prefill path plausible, especially for chunk B plus the last token. But its GDN mixer commits only lane 0 immediately; the remaining accepted lanes require record-and-fold. Its normal tail performs speculative acceptance and may select the fast head. Known prompt tokens must all commit irrespective of predicted successors, so reusing the production verify graph wholesale is incorrect. Evidence: [engine.cuh:2056](/mnt/ai/projects/q27/src/engine.cuh:2056), [engine.cuh:2087](/mnt/ai/projects/q27/src/engine.cuh:2087), [engine.cuh:2321](/mnt/ai/projects/q27/src/engine.cuh:2321), [engine.cuh:2342](/mnt/ai/projects/q27/src/engine.cuh:2342).

   Estimate **2–4 sessions** for a dedicated path and gates. Price the required fold, taps, positions and single final head together. Routing through verify’s g32 kernels is another numerical change relative to current tiny g64 prefill. Walking five tokens through serial graphs also means five target weight streams.

   Graph-capturing chunk B itself is another candidate, but less cheap than capturing the last-token step: prefill bakes host `base` and T into launches and uses shared scratch. Avoid a graph cache indexed by every absolute position. The existing small-T GEMM dispatch already selects NT=16/32/64, so that basic optimization has been taken. Evidence: [engine.cuh:3853](/mnt/ai/projects/q27/src/engine.cuh:3853), [prefill.cu:889](/mnt/ai/projects/q27/src/prefill.cu:889).

6. **[P1] Require gates that actually exercise the changed serving path.**

   The existing batched NLL loop calls `prefill_chunk` directly and computes batched heads. It bypasses `generate_prefill`, P8 snapshots and the final-token handoff. It can validate kernel changes such as C, but cannot establish A or B’s orchestration correctness. Add a teacher-forced turn-replay gate through `generate_prefill`, including first-token NLL, warm suffix lengths, restore tiers and content/depth buckets. Otherwise B’s effect can be diluted or absent from the measurement. Evidence: [engine.cu:1070](/mnt/ai/projects/q27/src/engine.cu:1070).

   Use the prior split-K **+2% aggregate or segment NLL regression** trigger as a preregistered rejection ceiling, alongside isolated numerical checks, serial canonicals, deterministic repeats within each arm and representative agentic quality. For numerical variants, seeded old/new byte identity is diagnostic rather than a universal requirement; assess distributions and task outcomes. Measure DFlash2 tokens per round and total request wall as well as prefill wall, since degraded warming can erase the saving. The historical split-K result was much tighter than its ceiling: +0.018% aggregate and +0.063% worst segment. Evidence: [BUILDLOG.md:7754](/mnt/ai/projects/q27/docs/BUILDLOG.md:7754).

   Test A/B/C independently, then together. Use separate candidate cache roots for numerical experiments, retaining the existing DFlash2-versus-ladder MTP separation. For general-mode changes, exercise shared-arena ownership and copy final outputs into engine-owned storage before yielding. DFlash2 production currently **requires `Q27_BATCH=0`**; preserve that guard, while testing ladder batch mode separately because it shares `generate_prefill`. Evidence: [prefill_arena.h:117](/mnt/ai/projects/q27/src/prefill_arena.h:117), [server.cu:535](/mnt/ai/projects/q27/src/server.cu:535), [server.cu:1770](/mnt/ai/projects/q27/src/server.cu:1770).

7. **[P1/P3] Tomorrow: graph capture, then a bounded C experiment; defer broader rewrites.**

   First implement and verify the tapped-token graph. Next use the existing `Q27_PF_SPLIT` override to compare 1/2/4/8 splits at the actual warm-turn depths and T≈5/36/64/128, including combine cost. If the win survives, implement C’s guarded dispatch and run its quality gates. Then undertake narrowly scoped B. Reprice A after those gains, because eliminating a chunk becomes less valuable once that chunk is cheaper.

   Explicitly defer A’s general bitwise machinery, a new tiny verify pipeline, long-context attention rewrites and WY parallelization. Do not raise the eight-split capacity merely to reach 170 blocks, move the stable boundary, drop the last DFlash2 row, or treat unchanged five-token canonicals as proof of serving correctness. The measured problem is repeated small-turn passes; the plan’s phase-4 rewrites address a different regime. Evidence: [prefill-attack.md:384](/mnt/ai/projects/q27/docs/plans/2026-09-08-prefill-attack.md:384), [prefill-attack.md:398](/mnt/ai/projects/q27/docs/plans/2026-09-08-prefill-attack.md:398).
